# Windows x64 Shellcode 分析报告

> **样本**：`WinExec("calc.exe")` shellcode（209 字节，x64，位置无关）
> **构建方式**：C 源码 + 原生 `cl.exe`（MSVC 14.50 / VS 2026 BuildTools）编译，抠出 `.text$sc` 段
> **实测**：直接调用、以及把抠出的字节丢进 RWX 内存执行，均成功弹出计算器
> 作者：Reasonix ｜ 用途：shellcode 原理学习 / 教学分享

---

## 0. TL;DR

| 指标 | 值 |
|---|---|
| 大小 | **209 字节** |
| 架构 | x86-64（PE32+ 代码段） |
| 位置无关 (PIC) | ✅ 无绝对地址重定位 |
| 依赖导入表 | ❌ 不需要（运行时手动解析 kernel32 导出） |
| 空字节 | ⚠️ **含**（编译器生成，见 §6.1） |
| 行为 | 弹出 `calc.exe` |
| 关键手法 | PEB 遍历 → 导出表解析 → ROR13 哈希找 `WinExec` → 栈上拼串 → 间接调用 |

一句话：**不 import、不 reloc、gs:[0x60] 摸 PEB、靠哈希认 API**，这是"注入后原地起爆"的经典 shellcode 形态。

---

## 1. 目标与约束

目标是做一段能在任意 64 位 Windows 进程内存里**直接执行**的代码，且满足 shellcode 的固有约束：

1. **位置无关（PIC）**——加载地址未知，任何绝对地址引用都会失效；
2. **不依赖导入表**——被注入的进程未必加载了我们需要的 DLL，也不知道 `WinExec` 的地址，得自己找；
3. **可落字节流**——要能从文件读入内存直接跑。

选择 `WinExec("calc.exe")` 作为行为，是因为它是公认的**良性 PoC**：证明代码确实执行了，又不产生实际危害。

## 2. 技术路线

### 2.1 位置无关：一切从寄存器出发

代码里没有任何全局变量、没有字符串常量（会落到 `.rdata` 产生绝对地址引用）、没有 `call [got]`。所有地址都在运行时**从寄存器/栈上算出来**。

### 2.2 通过 PEB 找 kernel32

x64 下 TEB 在 `gs` 段寄存器，`gs:[0x60]` 就是 PEB。沿固定偏移走：

```
gs:[0x60]           -> PEB
PEB  + 0x18         -> PEB->Ldr
Ldr  + 0x20         -> InMemoryOrderModuleList.Flink   (第 1 项 = 可执行自身)
[Flink]             -> 第 2 项 = ntdll.dll 的 InMemoryOrderLinks
[Flink]             -> 第 3 项 = kernel32.dll 的 InMemoryOrderLinks
+ 0x20              -> 该模块的 DllBase
```

> 偏移推导：`LDR_DATA_TABLE_ENTRY` 里 `InMemoryOrderLinks` 在 `+0x10`、`DllBase` 在 `+0x30`，所以从"链接指针"再 `+0x20` 就是 `DllBase`。

### 2.3 导出表 + ROR13 哈希认 API

拿到 kernel32 基址后解析 PE 导出目录：

```
e_lfanew      = [base + 0x3C]
导出目录 RVA   = [base + e_lfanew + 0x88]     ; e_lfanew + 18h(可选头) + 70h(导出项)
导出目录:
  +0x18 NumberOfNames          +0x1C AddressOfFunctions
  +0x20 AddressOfNames         +0x24 AddressOfNameOrdinals
```

遍历 `AddressOfNames`，对每个函数名做 **ROR13 哈希**：

```
h = 0
for c in name:  h = ror32(h, 13) + c        ; 不包含结尾 '\0'
```

命中 `ROR13("WinExec") == 0x0E8AFE98` 后，用对应序号到 `AddressOfFunctions` 取函数 RVA，加基址即得 `WinExec` 的实际地址。

> 为什么用哈希而不是明文比较？明文函数名会以可读字符串形式出现在 shellcode 里，容易被静态特征匹配；哈希把"我要哪个 API"压成一个常量。

### 2.4 栈上拼字符串

`"calc.exe"` 不能做成字符串常量（会进 `.rdata`）。做法是把 8 字节直接写栈：

```c
char cmd[16];
*(volatile unsigned __int64*)cmd = 0x6578652e636c6163ULL; // 小端 = "calc.exe"
cmd[8] = 0;
```

`volatile` 是关键——不加，`/O2` 很可能把它优化成对 `.rdata` 常量的 `memcpy`，于是产生绝对地址，PIC 就破了。

### 2.5 调用

把 `WinExec` 地址装进寄存器，间接 `call`：

```
WinExec("calc.exe", SW_SHOWNORMAL=1)
```

## 3. 工程结构

| 文件 | 作用 |
|---|---|
| `shellcode.c` | C 载荷（`sc_payload` 在独立段 `.text$sc`）。**这就是 shellcode 的源码** |
| `go.bat` | 一键流水线：编译 → 抠字节 → 跑 C 载荷 → 跑抠出的 shellcode |
| `extract.py` | 解析 `shellcode.obj`，取 `.text$sc` 段原始字节 → `shellcode.bin`，并用 capstone 反汇编 |
| `loader.py` | 把 `shellcode.bin` 读入 RWX 内存并执行（证明其为独立可用 shellcode） |
| `shellcode.obj` / `shellcode.exe` | `cl` 产物 |
| `shellcode.bin` | 抠出的 209 字节 shellcode |
| `calc_nf.asm` / `go_asm.bat` / `shellcode_asm.bin` | 变体 1：手写汇编 null-free（见 §9） |
| `gen_priv.py` / `priv_sc.c` / `go_priv.bat` / `loader_priv.py` / `priv_sc.bin` | 变体 2：令牌提权（见 §11） |

**为什么单独放一个段？** 用 `#pragma code_seg(".text$sc")` + `/Gy`（函数级 COMDAT），让 `sc_payload` 独占一个 COFF 段。这样"该段的原始字节 == shellcode"——不用去猜函数的起止，直接段内取字节，稳。

## 6. 关键发现

### 6.1 含空字节——C 编译 shellcode 的固有代价

字节流里出现 `00` 的位置：`[16,17,18, 49,50,51, 71,72,73, 78,79, 174,175,176, 194]`。

根源是 x86-64 的立即数/位移编码：

- `mov rax, gs:[0x60]` → `... 25 60 00 00 00`（`0x60` 补 4 字节零）
- `sub rsp, 0x30` / `cmp ..., 0x88` 之类小常量 → 高位补零

**影响**：如果把 shellcode 通过 `strcpy`/`sprintf` 这类"遇 0 截断"的路径注入，它会被砍断。要么改用不截断的注入通道，要么先做**编码**（`shikata_ga_nai`、异或、字母表编码等）。

**对比**：手写汇编可以刻意挑选 `xor eax,eax` + `mov al,0x60`、`push/pop` 等"无零"指令来规避。C 编译器不关心这个——这是 C 路线的固有短板。想要干净 null-free，还是得手写汇编（或用编码器后处理）。

### 6.2 体积

209 字节。C 出来的代码天然带了函数序言/尾声（`push rdi` / `mov [rsp+8],rbx` / `sub rsp,0x30` …）和保守的寄存器分配。同功能手写汇编实测能做到 **176 字节且 null-free**（见 §9 变体）——所以**体积不是主要差距**，「能不能有零字节」才是 C 路线的硬伤。

### 6.3 编译器重排

`/O2` 明显重排了寄存器分配（`AddressOfNames` 提前进 `ebx`、循环索引用 `r8d`），并且保留了一处 `nop word [rax+rax]`（0x4A）做**循环对齐**。这些都不影响语义，但读反汇编时要认得出"这是编译器的手笔，不是算法本身"。

### 6.4 关于 `.text$sc` 段恰好等于函数

本样本里 `.text$sc` 段的 `rawsize = 209`，去掉尾部填充后正好是完整函数（结尾 `c3` = `ret`），没有多余字节——所以不需要再修边。

## 7. 防御 / 检测视角（蓝队）

这段 shellcode 触发了多个**典型注入/逃逸特征**，检测点如下：

| 特征 | 观测方式 | 说明 |
|---|---|---|
| **RWX 内存页** | `VirtualAlloc(PAGE_EXECUTE_READWRITE)` | 正常 PE 的代码段是 RX；可写又可执行的私有内存是强信号 |
| **`gs:[0x60]` 直接读 PEB** | 指令级/ETW | 合法程序极少手搓 PEB，常见于 shellcode/loader |
| **导出表哈希遍历** | 行为/静态 | 进程内遍历 `AddressOfNames` 做哈希、而非用导入表 = API hashing 特征 |
| **无导入表的小代码块** | 内存扫描 | 一段自己能解析 API 的独立字节，本身就可疑 |
| **`WinExec`/`CreateProcess` 子进程** | 进程创建监控 | 可疑父进程(unusual parent) 派生 `calc.exe` 等 |
| **线程起始地址在私有内存** | `QueueUserAPC`/`CreateThread` 审计 | 执行起点不在任何模块的映射范围内 |

**缓解**：DEP/CFG/CET 抬高了门槛（本例是"数据即代码"，靠 RWX 绕过 NX——现代 EDR 对私有 RWX 页的生成/执行会记事件）；真正挡住的是**内存扫描（MQ/特征）+ 行为链**。

> 教学样本刻意无害；把 `calc.exe` 换成别的命令，检测点（尤其"进程创建"和"RWX 执行"）依然成立。

## 8. 局限与假设

1. **假设 kernel32 是 InMemoryOrderModuleList 的第 3 项**（自身 → ntdll → kernel32）。Win10/11 常规进程成立；更稳的做法是**对 DllBase 名字也做哈希**，不写死序号。
2. `WinExec` 是较老的 API（内部走 `CreateProcess`），但 kernel32 至今导出，可用。
3. **非 null-free**（见 §6.1），按需编码。
4. 未做反沙箱/反调试（延时、环境探测等），纯原理样本。

## 9. 变体：手写汇编 null-free 版（对照）

为对照 C 版的两个短板，另做了一版**手写汇编**（MASM `ml64` 汇编）：

| 指标 | C 版 `shellcode.c` | 汇编变体 `calc_nf.asm` |
|---|---|---|
| 大小 | 209 字节 | **176 字节** |
| 空字节 | **有**（15 处） | **无** ✔ |
| 汇编器 | `cl` (MSVC) | `ml64` (MASM) |
| 段 | `.text$sc` | `.text$mn` |
| 构建 | `go.bat` | `go_asm.bat` |

**null-free 手法**（详见 `calc_nf.asm` 注释）：

- 裸 `[reg]`（无位移）会编码出 `00` 字节（`48 8B 00` 的 ModRM = 0）→ 改用 `[reg+rcx]`（`rcx=0`）→ `48 8B 04 08`；
- 常量 `0x88` 落在 disp32 区间会补零 → 用 `xor r11d,r11d` + `mov r11b,88h` 在寄存器里拼；
- `SW_SHOWNORMAL=1` 用 `inc edx`（`mov edx,1` 会变 `...01 00 00 00`）；
- `"calc.exe"` 直接 `movabs` 进寄存器。

**踩坑（语义，值得单列）**：

> 跨 `call WinExec` 保存 `rsp` 时用了 **`r11`**——它是**易失寄存器**，被 `WinExec` 覆盖 → 返回后 `mov rsp, r11` 把栈指针恢复成垃圾 → **0xC0000005 访问违例**。
> 换成**非易失寄存器 `rbx`** 后正常。
> **教训：shellcode 里跨函数调用只用 `rbx/rbp/rsi/rdi/r12–r15` 存状态。**

复现：`go_asm.bat` → `ml64` 汇编 → `extract.py calc_nf.obj .text$mn shellcode_asm.bin` → `loader.py` RWX 执行，实测弹出计算器。

## 11. 变体 2：拿到访问权限 —— 自身令牌启用 SeDebugPrivilege

在 calc 的基础上，把技术从「解析单个 API」升级到「**引导链（bootstrap）」**：

1. hash 解析 kernel32 的 `LoadLibraryA` / `GetProcAddress`
   （`ROR13` = `0xEC0E4E8E` / `0x7C0DFCAA`，业界经典值）；
2. `LoadLibraryA("advapi32.dll")` —— 令牌 API 在 advapi32，PEB 模块链里通常没有，**必须现加载**；
3. `GetProcAddress` 依次取 `OpenProcessToken` / `LookupPrivilegeValueA` / `AdjustTokenPrivileges`；
4. `OpenProcessToken((HANDLE)-1, …)` 拿自身进程令牌 → `LookupPrivilegeValueA(NULL,"SeDebugPrivilege")` → `AdjustTokenPrivileges(…, SE_PRIVILEGE_ENABLED)`。

所有函数名/字符串都在**栈上**用 `volatile` qword 写入拼出（避免 `.rdata` 常量 → 保住 PIC）；函数名常量由 `gen_priv.py` 程序化计算，杜绝手抄出错。

| 指标 | 值 |
|---|---|
| 大小 | **618 字节** |
| 空字节 | 有（C 生成） |
| 涉及 DLL | kernel32（静态走 PEB）+ advapi32（`LoadLibraryA` 动态） |
| 证明方式 | loader 先手动禁用 → 跑 shellcode → 复查，`False → True` |

**实测输出**：

```
[*] SeDebugPrivilege BEFORE     : enabled=True
[*] manually DISABLED           : enabled=False
[*] running shellcode @ 0x1CCC6F50000 ...
[+] SeDebugPrivilege AFTER shellcode: enabled=True
    -> shellcode enabled the privilege
```

→ 证明该 shellcode 在自己的进程令牌上确实打开了 `SeDebugPrivilege`。
